## G4. Retargeting the review-escalation test cases

Keep each case's assertion and change only the operation and the skill it
names. Every `review-escalation` case tests the receipt check on a second
fresh-context operation bound to a second skill, so each one goes to
`doc-review`. The skill its calls name, `ce-code-review`, goes to
`ce-doc-review`, in the tests and in the Codex rollout fixtures they read.

by check. Its `review` row keeps `code-review` and carries the table's new

and allows no discovery rows, so a discovered binding is not an option there.

## G5. The receipt's exception field (R12)

The receipt gains a field after `Receipt check:`:

```text
Exception:       <the one failing receipt-check line, pasted as it printed, and why it fails and
                  why the story is ready all the same, for the lead to accept or send back — or
                  "none">
```

Step 8 pins the rule: `STATUS: ready` only on a receipt check that exits 0, or
on one failing line named under Exception. Two failing lines, or one that is
not named, is not ready. That means fixing them first, or a blocked hand-back.

## G6. Step 5's read instruction stays portable

It names the command as step 8 names the receipt check: `node "<supervision-setup's
folder>/scripts/review-read.mjs" --checkout "<the story's checkout>" --from <commit>`,
run alone as the reviewer's first call. `<commit>` is the base branch's commit
for a full review, or the last reviewed head for a re-check. The reviewer then
tells the performer to diff from the base it printed, by commit id. The
existing quote-and-compare check stays.

Step 5's docs-only definition (KTD6) names no repo path. It says every changed
path is a markdown file, and none is a skill's file, an agent instruction file
or a plugin manifest. A manifest change that touches only its version is
ignored.
