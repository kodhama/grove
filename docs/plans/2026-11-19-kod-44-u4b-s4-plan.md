### Problem Frame

Today `coverFrom` accepts a re-check whose base is the covered point **or any ancestor of it** (`skills/supervision-setup/scripts/review-coverage.mjs:163`), so content added, deleted before the full review and added again shows in no diff (gaps G10, the Z/W reproduction). `leadReviewed` compares commit ids (`review-coverage.mjs:190-191`), so an empty lead range, or one made of a clean base merge, unlocks carried evidence. `placed()` credits a review at the first chain commit with an equal `git patch-id --verbatim` (`review-coverage.mjs:118-125`), which ignores hunk positions. None of these can pass a pull request today, because `doc review: not checked (not built yet)` keeps every run at exit 1 or 2 (`merge-gate-checks.mjs:508`); they must close before S4b-2 removes that row.

## Planning Contract

### Key Technical Decisions

- KTD1. **Coverage is reachability over exact bases, from every eligible start.** A credited full review's place is reached. A clean base merge right after a reached place is reached. A re-check placed at `q` is reached when some reached place `p < q` has the same tree as the re-check's base (`git rev-parse <sha>^{tree}`). Coverage passes when the head's place is reached. Tree equality is used, not commit equality, because a diff depends only on the two trees: it lets a re-check from a reviewed side-branch head, or from a rebased head whose tree did not move, link without reading less (O1). The printed start is the furthest full review from which the head is reached, ties to the later call; with none, today's furthest start and its uncovered tail. `<k>` is the fewest re-checks on a path, and a path without carried links is preferred. This replaces `coverFrom`'s greedy furthest jump (`review-coverage.mjs:153-172`) and KTD4's "or an ancestor of it" (unit plan :111): a departure to name in S4a-1's PR.
- KTD2. **One merge-tree source for N8, N7 and F9.** `gate-sources.mjs` gains `treeOf(sha)` and `mergeTree(a, b)`: `git merge-tree --write-tree a b`, returning the tree on exit 0, null on exit 1 (conflict), and a `TransportFailure` otherwise. `--write-tree` needs git 2.38, under the gate's 2.39 floor (`gate-sources.mjs:71`). `--merge-base` is not used, since it needs a newer git (unverified, O-claims). Where a replay needs a specific merge base, the gate first checks that `git merge-base --all a b` is exactly that one commit, and fails closed otherwise. Checked on git 2.39.5: a clean merge's parents re-merge to its tree.
- KTD3. **N8: a clean base merge has two parents, its second an ancestor of the base, and `mergeTree(p1, p2)` equal to its own tree.** This replaces the `listed` set from `nonTestLines` in `cleanMerge` (`review-coverage.mjs:144-146`, `:206-207`), so the rule no longer depends on which range was counted. Octopus merges and any conflict (merge-tree exit 1, hidden or not) are never clean. Today's remerge-numstat test agrees on every case found (a mode-only change in a merge shows a `0 0` numstat row and is listed); the merge-tree compare is the ruled definition and serves N7 and F9 too. The line count keeps `nonTestLines` unchanged.
- KTD4. **N7: PR content by runs, plus the 11-15 tree check.** Over the lead record's own range, `lead.base..head` by `firstParentChain`, classify each commit with KTD3's `cleanMerge`; the rest are PR content (non-merge commits, side-branch merges, octopus merges, base merges that do not re-merge clean). Group PR content into runs between skipped merges; a run's net is its first commit's first parent's tree against its last commit's tree. Then: no runs, or every run empty, reads no PR content; exactly one non-empty run reads PR content; two or more non-empty runs read PR content only when `Q = mergeTree(lead.base, B)` succeeds, where `B` is the last skipped merge's second parent and every skipped merge's second parent is an ancestor of `B`, and the head's tree differs from `Q` at some path a non-empty run changed. Anything else does not unlock (fail closed). **The 11-15 tree check still applies** as a separate conjunct: the lead's base tree must differ from the head's, or the lead read nothing. A lead base that is not an ancestor of the head unlocks nothing.
- KTD5. **F9: placement needs the patch-id and the replayed tree.** A record placed by patch-id sits at the first chain commit `c` whose patch-id matches (as today) and whose tree equals the replay: `tree(r.head)` for a side-branch record (its diff runs from `M`), and `mergeTree(M, r.head)` for a KTD7 rebase, after checking that `r`'s own merge-base is the only merge base of `M` and `r.head`. A conflict or any other doubt places nothing. Checked on git 2.39.5 with the reproduction U3 writes: the review's diff, a correct rebase and a wrong-place edit all share one patch-id; the review and the wrong-place edit share hunk header `-6,7 +6,7`; the correct rebase's header is `-18,7 +18,7`; `merge-tree` gives the correct rebase's tree and not the wrong one's. So "hunks with positions" would accept the wrong edit and refuse the rebase, and "post-image at the touched paths" would refuse both, since the upstream shift changes that file. Equal trees are not required: the replay is the rebased tree.
- KTD6. **Rollout descent is a record tag, by thread membership.** `readReviewReads` computes each named rollout's descendant threads from its own child records, whatever walk reaches them, and tags every record whose thread is a named rollout or one of those descendants. The gate's `rollout` tag (`merge-gate-checks.mjs:236`) reads that tag. The `rollouts` return field (`review-reads.mjs:443-447`, `:487`) goes, since its only consumer moves to the tag.
- KTD7. **Trust checks location and content.** A read script is trusted when its realpath is in the trusted set (as today) and its bytes equal the gate's own sibling `review-read.mjs`. A mismatch gives `read script differs from the gate's copy`. A relative table path resolves by walking up from the bindings file, as setup does (`routing-table.mjs:53-62`), and gives no trusted copy when nothing is found; it never falls back to `--checkout` or the working directory.
- KTD8. **Records do not depend on `--bindings` order.** A local record is kept once per role whose file binds its skill, de-duplicated by key and role, not by key alone (`merge-gate-checks.mjs:224`, `:233`). A carried line yields one record per distinct binding among its owners (`:206`). Each is what that file alone would have given.
- KTD9. **G10: a Codex skill use is credited on its read alone** when its tree is clean, its read is the last read-like command before the use in the same rollout with no other read between them, and its base meets KTD1 (a full review's own merge-base; a re-check's base tree-equal to a reached place). Records gain `host`. A read-like command (its line names `review-read.mjs`) that yields no triple, failed or chained, resets the triple on both hosts. A carried line never takes read-alone credit: the handoff holds no adjacency evidence. A Claude call's bare skill name stops matching a namespaced binding if U5 confirms Claude can record one (unconfirmed).
- KTD10. **G9: a doc path is reviewed when a creditable `doc-review` record names it (Claude) or covers it (Codex, a path changed in `base..r.head`), its head is an ancestor of the head, and no commit in `r.head..head` touches the path** (`git rev-list -n 1 r.head..head -- <path>`, empty). A doc-review record needs no base in its args, since it names documents (unit plan KTD6, O7). KTD6's docs-only rule and doc-review re-checks over docs-only ranges follow G9 as written.
- KTD11. **Six slices, sized by the gate's own count.** See Sizing.

### High-Level Technical Design

Directional, not implementation. Coverage after S4a-1 (KTD1):

```text
places:  M  A   B   m(clean base merge)  C   D=head
full review at A ............ reached {A}
clean merge edge ............ (only from a reached place right before it)
re-check base tree == tree(A), head C ... reached {A, C}
re-check base tree == tree(C), head D ... reached {A, C, D}  -> pass, 2 re-checks
re-check base B (not reached) ........... no edge (Z/W closed)
```

N7's decision over the lead range (KTD4):

```text
lead.base ancestor of head?  no -> no unlock
tree(lead.base) == tree(head)? yes -> no unlock          (11-15 tree check)
runs = PR-content commits between clean base merges (KTD3)
  no non-empty run          -> no unlock
  one non-empty run         -> unlock
  two or more               -> Q = mergeTree(lead.base, B)
                               Q null or B not newest -> no unlock
                               head differs from Q at a run-touched path -> unlock
                               else -> no unlock
```
