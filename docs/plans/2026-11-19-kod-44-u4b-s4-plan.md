## Planning Contract

### Key Technical Decisions

- KTD1. **Coverage is reachability over exact bases, from every eligible start.** A credited full review's place is reached. A clean base merge right after a reached place is reached. A re-check placed at `q` is reached when some reached place `p < q` has the same tree as the re-check's base (`git rev-parse <sha>^{tree}`). Coverage passes when the head's place is reached. Tree equality is used, not commit equality, because a diff depends only on the two trees: it lets a re-check from a reviewed side-branch head link without reading less (O1, ruled 11-19). A read from a pre-rebase head after a rebase onto the same base needs no such link: `review-read.mjs` records the merge-base of `HEAD` and `--from` (`review-read.mjs:10`, `:91`), here the fork point, so `placed()` credits it as a full review (`review-coverage.mjs:110-111`). The printed start is the furthest full review from which the head is reached, ties to the later call; with none, today's furthest start and its uncovered tail. `<k>` is the fewest re-checks on a path, and a path without carried links is preferred. This replaces `coverFrom`'s greedy furthest jump (`review-coverage.mjs:153-172`) and unit-plan KTD4's "or an ancestor of it" (unit plan :111): a departure to name in S4a-1's PR. **A second departure for S4a-1's PR:** the printed start can be earlier than the latest full review, and the 150-line count runs from the printed start (`review-coverage.mjs:206`), which is stricter than unit-plan KTD5's "since the last full review". Until S4a-2 replaces it (KTD3), `listed` comes from `nonTestLines(M, head, baseSha).merges`, not from the printed start's range (`review-coverage.mjs:206-207`): a range from a later start omits the merges before it, so a merge with remerge rows between an earlier start and a later one would be stepped over as clean.
- KTD2. **One merge-tree source for N8, N7 and F9.** `gate-sources.mjs` gains `treeOf(sha)` and `mergeTree(a, b)`: `git merge-tree --write-tree a b`, returning the tree on exit 0, null on exit 1 (conflict), and a `TransportFailure` otherwise. `--write-tree` needs git 2.38, under the gate's 2.39 floor (`gate-sources.mjs:71`). `--merge-base` is not used, since it needs a newer git (unverified, O-claims). Where a replay needs a specific merge base, the gate first checks that `git merge-base --all a b` is exactly that one commit, and fails closed otherwise. Checked on git 2.39.5: a clean merge's parents re-merge to its tree.
- KTD3. **N8, ruled by the lead 11-19 (O9, "my N8 ruling made concrete"): a clean base merge has two parents, its second an ancestor of the base, and `mergeTree(p1, p2)` equal to its own tree.** A conflict (merge-tree exit 1, hidden or not), or more than one merge base of `p1` and `p2` (KTD2's check), fails closed: the merge is not clean. S4a-2 builds it, replacing the `listed` set from `nonTestLines` in `cleanMerge` (`review-coverage.mjs:144-146`, `:206-207`). The reason is not range: once S4a-1 takes `listed` from `M..head` (KTD1), it no longer depends on which range was counted. The compare is R2's own words, re-merge the two parents and compare trees byte for byte, asked of one merge alone; `listed` answers that indirectly, through remerge-diff numstat rows plus a separate scan for conflict notices those rows lack (`gate-sources.mjs:596-598`, `:619`, `hasHiddenConflict` `:498-502`). And the same `mergeTree` serves N7 and F9 (KTD2). Today's remerge-numstat test agrees on every case found (a mode-only change in a merge shows a `0 0` numstat row and is listed). Octopus merges are never clean for coverage, so coverage never steps over them; N7 classifies an octopus per O11 (KTD4). The line count keeps `nonTestLines` unchanged.
- KTD4. **N7: PR content by runs, unlocked only through a witness path, plus the 11-15 tree check.** **The range is anchored by tree.** The anchor `a` is the latest place on the chain `M..head` (or `M` itself) whose tree equals `tree(lead.base)`; with none, the record does not unlock. The lead's diff `lead.base..head` is the same diff as `a..head`, since a diff depends only on its two trees, so the anchor reads exactly what the lead read. Without it, a lead base `S1` that is a side head merged no-ff at chain commit `s` would give `rev-list --first-parent S1..head` (`gate-sources.mjs:427-431`) the commit `s` and the chain commits since `S1`'s fork point, one non-empty run, and unlock, though `tree(s) == tree(S1)` and the lead read only what the base merges after `s` brought. **Base merges never unlock carried evidence (lead, 11-19, about 08:40Z, tightening the 11-18 text).** Over `a..head` by `firstParentChain`, only two kinds of commit are PR content, and witnesses come only from them: a non-merge commit, and a PR side-branch merge (two parents, the second not an ancestor of the base). Every other merge in the range is a base merge, one whose non-first parents are all ancestors of the base, and none is PR content. A base merge KTD3 finds clean is skipped, as before. A base merge KTD3 refuses (more than one merge base of its parents, or any conflict resolution, conflict-to-ours included) gives no unlock and supplies no witness paths; coverage still needs its own re-check (unit-plan KTD5's "a re-check of its own"). This fails closed. **O11 is a special case of this rule:** an octopus whose non-first parents are all ancestors of the base is a base merge, and KTD3 never finds it clean, so it too gives no unlock and supplies no witness; no tree check is made (lead ruling 3, 11-20). An octopus with a parent that is not an ancestor of the base is no PR content and means no unlock, as O11 ruled. Group PR content into runs between base merges, skipped or refused; a run's net is its first commit's first parent's tree against its last commit's tree, and the paths a run changed are the paths in that net, so a base merge's own paths are in no run. **The base-only tree `Q`** is `mergeTree(a, M)`, `M` the head's merge base with the live base, with two single-base checks that fail closed: `git merge-base --all head base` is exactly `M`, and `git merge-base --all a M` is exactly one commit; a conflict or a failed check means no unlock (lead ruling 11-20). A refused base merge counts in `Q` as a skipped one does. Where the PR change a refused merge conflicted with sits at or before `a`, `mergeTree(a, M)` itself conflicts and nothing unlocks. **The witness-path rule, for one run and for many:** the record unlocks only when some path `p` that a non-empty run changed has `Q` equal to `tree(a)` at `p` and the head's tree different from `tree(a)` at `p`. With no non-empty run there is no witness. **The comparison is per path, by blob and mode, not per hunk,** so two unrelated hunks cannot split it: `Q` and `tree(a)` are compared over the whole of `p`. Hunk-level comparison was not chosen: it rests on hunk positions, which KTD5 shows an upstream shift moves. The price fails closed: a PR whose every changed path the base also changed does not unlock, nor does a range whose only content beside its base merges is upstream's; the lead's own full review, or a re-check based past the base merge, is the remedy. Walk-throughs, each a U2 test: (1) the same-file variant: at `a`, `f` holds hunks (A, x); the PR changes A to B; a clean base merge brings the same A to B plus x to y; a PR commit reverts B to A. The head's `f` is (A, y), `Q`'s is (B, y), `tree(a)`'s is (A, x). `Q` differs from `tree(a)` at `f`, so `f` is no witness, and nothing unlocks, though the head differs from both (this plan's earlier "differs from both `Q` and `tree(a)`" test unlocked it, and the lead's diff holds only upstream's x to y). (2) The one-run case: after `a`, a clean base merge brings `f` A to B plus `g`; one PR commit restores `f` to A. `Q`'s `f` is B, not A, so `f` is no witness; no run changed `g`; nothing unlocks (the earlier one-run rule unlocked it). (3) A real change still unlocks: the PR changes `f` A to B, and a clean base merge touches only `g`. `Q`'s `f` is A, equal to `tree(a)`'s, and the head's is B, so `f` is a witness, with one run or with a later run touching another path. (4) A refused base merge beside a real change: after `a`, PR commit `c1` edits `g`; base merge `m`, whose base side edits `g` and `h`, conflicts at `g` and is resolved by hand; PR commit `c2` edits `f`. The runs are `[c1]` and `[c2]`, and `m` is in neither. `Q` is `mergeTree(a, M)`, clean since `a` holds the original `g`, with the base's `g` and `h`. `g` is no witness (`Q` differs from `tree(a)` there), `h` is in no run, and `f` is a witness: the record unlocks through `c2` alone. Without `c2` nothing unlocks; before the 11-19 ruling `m` was PR content and its `h` a witness. Residual, accepted (O4): `Q` is one re-merge against `M`, not each base merge in turn, skipped or refused. Anything else does not unlock (fail closed). A side-branch merge that wraps a base merge is closed by `Q = mergeTree(a, M)` (lead ruling 1, 11-20), pinned by the X1 and F2(b) tests. **The 11-15 tree check still applies** as a separate conjunct: the lead's base tree must differ from the head's, or the lead read nothing. A lead base that is not an ancestor of the head unlocks nothing.
- KTD5. **F9, ruled by the lead 11-19 (O10, "same change, same place" made concrete): placement needs the patch-id and the replayed tree.** S4a-3 builds it, and turns the reproduction below into a test: the wrong-place edit is refused, the correct rebase accepted (U3). It narrows unit-plan KTD7's "A match credits it": a departure to name in S4a-3's PR. A record placed by patch-id sits at the first chain commit `c` whose patch-id matches (as today) and whose tree equals the replay: `tree(r.head)` for a side-branch record (its diff runs from `M`), and `mergeTree(M, r.head)` for a unit-plan KTD7 rebase, after checking that `r`'s own merge-base is the only merge base of `M` and `r.head`. A conflict, more than one merge base, or any other doubt places nothing. Checked on git 2.39.5 with the reproduction U3 writes: the review's diff, a correct rebase and a wrong-place edit all share one patch-id; the review and the wrong-place edit share hunk header `-6,7 +6,7`; the correct rebase's header is `-18,7 +18,7`; `merge-tree` gives the correct rebase's tree and not the wrong one's. So "hunks with positions" would accept the wrong edit and refuse the rebase, and "post-image at the touched paths" would refuse both, since the upstream shift changes that file. Equal trees are not required: the replay is the rebased tree.
- KTD6. **Rollout descent is a record tag, by thread membership.** `readReviewReads` computes each named rollout's descendant threads from its own child records, whatever walk reaches them, and tags every record whose thread is a named rollout or one of those descendants. The gate's `rollout` tag (`merge-gate-checks.mjs:236`) reads that tag. The `rollouts` return field (`review-reads.mjs:443-447`, `:487`) goes, since its only consumer moves to the tag.
- KTD7. **Trust checks location and content.** A read script is trusted when its realpath is in the trusted set (as today) and its bytes equal the gate's own sibling `review-read.mjs`. A mismatch gives `read script differs from the gate's copy`. A relative table path resolves by walking up from the bindings file, as setup does (`routing-table.mjs:53-62`), and gives no trusted copy when nothing is found; it never falls back to `--checkout` or the working directory.
- KTD8. **Records do not depend on `--bindings` order.** A local record is kept once per role whose file binds its skill, de-duplicated by key and role, not by key alone (`merge-gate-checks.mjs:224`, `:233`). A carried line yields one record per distinct binding among its owners (`:206`). Each is what that file alone would have given, except that a record kept for both a lead file and a worker file gets no patch-id credit on its worker copy, as G7's lead ruling 2 gives none to any lead record (gaps:318; O12, ruled 11-19); it still places where its own head is on the chain.
- KTD9. **G10: a Codex skill use is credited on its read alone** when its tree is clean, its read is the last read-like command before the use in the same rollout with no other read between them, and its base meets KTD1 (a full review's own merge-base; a re-check's base tree-equal to a reached place). Records gain `host`. A read-like command (its line names `review-read.mjs`) that yields no triple, failed or chained, resets the triple on both hosts. A carried line never takes read-alone credit: the handoff holds no adjacency evidence. A Claude call's bare skill name stops matching a namespaced binding if U5 confirms Claude can record one (unconfirmed). Read-alone credit departs from unit-plan KTD3 and unit-plan KTD6 (gaps, Departures, S4): S4b-1's PR names it.
- KTD10. **G9: a doc path is reviewed when a creditable `doc-review` record names it (Claude) or covers it (Codex, a path changed in `base..r.head`), its head is an ancestor of the head, no commit in `r.head..head` touches the path** (`git rev-list -n 1 r.head..head -- ':(literal)<path>'`, empty), **and the path's content at the head is the reviewed content** (`git diff --quiet <r.head> <head> -- ':(literal)<path>'` exits 0). Both commands pass the path as a `:(literal)` pathspec, the convention the gate's line count already uses (`gate-sources.mjs:487`), so a doc name holding `*`, `?` or `[` matches only itself. ### High-Level Technical Design

Directional, not implementation. Coverage after S4a-1 (KTD1):

```text
places:  M  A   B   m(clean base merge)  C   D=head
full review at A ............ reached {A}
clean merge edge ............ (only from a reached place right before it)
re-check base tree == tree(A), head C ... reached {A, C}
re-check base tree == tree(C), head D ... reached {A, C, D}  -> pass, 2 re-checks
re-check base B (not reached) ........... no edge (Z/W closed)
```

N7's decision over the lead range (KTD4):

```text
lead.base ancestor of head?  no -> no unlock
tree(lead.base) == tree(head)? yes -> no unlock          (11-15 tree check)
a = latest place in M..head with tree(a) == tree(lead.base); none -> no unlock
classify a..head (lead, 11-19: base merges never unlock):
  non-merge commit, or a PR side-branch merge  -> PR content (witnesses come only from these)
  base merge KTD3 finds clean                  -> skipped
  base merge KTD3 refuses (two merge bases, any conflict resolution, conflict-to-ours;
    an octopus whose other parents are all on the base) -> not PR content, no witness; coverage re-checks it
  an octopus with a parent off the base        -> no unlock
runs = PR content between base merges; no non-empty run -> no unlock
Q = mergeTree(a, M), M the head's merge base with the live base   (skipped and refused alike)
  merge-base --all head base not exactly M, merge-base --all a M not exactly one,
  or a conflict                                -> no unlock
witness = a path a non-empty run changed, with Q == tree(a) there and head != tree(a) there
  some witness -> unlock          (one run or many)
  none         -> no unlock
```
