## G2. Arguments

The full KTD2 list is parsed now, so the command line does not change in U4b.

| Argument | Required | U4a reads it |
| --- | --- | --- |
| `--pr <owner/repo#n>` | yes | yes. Owner and repo match `[A-Za-z0-9_.-]+`, `n` is a positive integer |
| `--head <sha>` | yes | yes. 40 or 64 lowercase hex, the pattern `gate-sources.mjs` uses |
| `--bindings <path>` | at least once, repeatable | no: parsed and kept for U4b |
| `--receipt <path>` | no | yes (G4) |
| `--carried <path>` | no | no: parsed and kept for U4b |
| `--codex-rollout <path>` | no, repeatable | no: parsed and kept for U4b |
| `--bot <name>` | no, repeatable | yes (G5) |
| `--bot-unavailable <name>:<reason>` | no, repeatable | yes (G5). The reason is non-empty and on one line |
| `--checkout <dir>` | no, defaults to the working directory | yes, for git (G6) and as the folder gh runs in |
| `--help` | no | prints the usage to stdout and exits 0, only as the sole argument |

Bad arguments exit 2 with `merge-gate: <reason>` and the usage line on
stderr, and nothing on stdout, before any process runs. Bad arguments are: a
missing or malformed required argument, an unknown option, a positional
argument, an empty `--bot` name, a `--bot-unavailable` value with no colon,
an empty name or a blank reason, a reason with a line break, one name given
to both `--bot` and `--bot-unavailable`, and `--help` alongside any other
argument. The usage line names the script as
`merge-gate.mjs`, with no path.

## G3. Entry point and exit codes

- `export function main(argv, { run, stdout, stderr })` returns the exit
  code. `run` defaults to `defaultRunner` from `gate-sources.mjs`; `stdout`
  and `stderr` default to the process streams. The file ends with
  a realpath guard that resolves both `process.argv[1]` and the module's own
  path, so a test imports `main` without running it and a symlinked install
  run with `--preserve-symlinks` still runs the gate (review fix; the older
  scripts' one-sided guard goes to U4b).
- **Every condition runs, each in its own try block.** A `TransportFailure`
  makes that condition's line `could not check (<call>: <reason>)`; the other
  conditions still run.
- **Exit 1 when any line is `fail`.** Otherwise exit 2 when any line is
  `could not check` or `not checked`. Otherwise exit 0. A found failure is
  definite, so a failure elsewhere to read cannot turn a 1 into a 2 (D1).
  This departs from KTD9's "exit 2 is for transport failures only": a
  `not checked` coverage line, and a missing commit or no merge-base for
  the attributes read, also exit 2 when nothing fails.
  In U4a the coverage line is always `not checked`, so **U4a never exits 0**
  from a run that checks a pull request: it exits 1 or 2.
- Any other thrown error exits 2 with `merge-gate: internal error: <message>`
  on stderr. A bug never exits 0 and never reads as a failed condition.

## G4. The lines, in order

Every line is `<condition>: <verdict> <reason>`. The verdicts extend KTD2's
pass, fail, carried and unavailable with `could not check`, `not checked`
and `warn`, plus the `blocked` last line (D1); U6 reads them as listed here.
Text that comes from GitHub or a process (check names, bot logins, thread
paths, an earlier review's commit id, transport-error reasons) is
JSON-escaped without the surrounding quotes: `JSON.stringify`'s own escapes
(such as `\n`), and `\uXXXX` for U+2028, U+2029, U+0085 and every other Cc,
Zl or Zp character it leaves raw, so none can start a line of its own
(review fix: `JSON.stringify` alone leaves U+2028 raw). Only check names,
bot names and thread paths print inside double quotes. `<sha>` is always `--head`.
Every condition reads `--head`, never the live head, so a moved head cannot
make one condition check another commit.

1. **Head (R1, AE4).** `head()` once. Its `sha` and `baseSha` must both match
   the SHA pattern, or the answer is malformed: `could not check (head:
   invalid sha from gh)`, exit 2 unless another line fails. The receipt is
   compared with `--head` even when `head()` fails (review fix). Then it fails, with every reason that
   applies joined by `; `, when the pull request's `state` is not `open`,
   when `--head` differs from the live head, and, with `--receipt`, when it
   differs from the receipt's shipped revision.
   - `head: pass <sha> is the live head[ and the receipt's shipped revision]`.
   - `head: fail --head <sha> is not the live head <live>`; `... is not the
     receipt's shipped revision <x>`; `the pull request is <state>`.
   - **The receipt** is the story receipt (`skills/story-worker/references/receipt.md`).
     Its shipped revision is the first token after `Shipped revision:` at a
     line's start, leading spaces allowed. No such line, two or more, or not
     7 to 40 hex characters: `head: fail the receipt has no single Shipped
     revision line with a 7 to 40 character hex sha` (readable evidence,
     exit 1). The value may be
     7 to 40 hex characters, since the receipt template asks only for the
     head SHA, and passes when it is a prefix of `--head`, ignoring case
     (review fix; the first draft required a full SHA). A receipt
     path that is not a readable file exits 2 before any process runs.
   - When `head()` fails and the receipt mismatches, the line is
     `head: fail <receipt reason>; could not check (head: <reason>)`.
2. **CI (R2).** `checks(<sha>)`. A check passes only when it is completed
   with conclusion `success`, `neutral` or `skipped`, the conclusions GitHub
   treats as passing for a required check. Running, a null conclusion on a
   completed check (never success), and every other conclusion fail. Every
   row counts; none is deduplicated by name. **At least one reported check
   must conclude `success`**: all-neutral or all-skipped fails R2, so a pull
   request whose CI never ran cannot pass (lead, 11-12):
   `ci: fail no check concluded success on <sha>`.
   - `ci: pass <n> checks passed on <sha>`.
   - `ci: fail no checks reported on <sha>`.
   - `ci: fail "<name>" <conclusion>, "<name>" still running, "<name>" completed with no conclusion`, one line naming every failing check.
3. **Review coverage (R3, R4, R8).** Always `review coverage: not checked
   (not built yet)`. U4b replaces the line.
4. **Threads (R5).** `threads()`, which paginates. A thread blocks when
   `isResolved` is false, outdated or not.
   - `threads: pass none unresolved`.
   - `threads: fail <n> unresolved: "<path>", "<path>"`.
5. **Bots (R6), G5.** One line per named bot, in the order given, then one
   per unnamed bot that reviewed, by login. With no bot named and none
   reviewing: `bots: pass none named and no other bot reviewed`. A failure
   of `botReviews` gives one line, `bots: could not check (<call>: <reason>)`,
   since nothing about any bot can be decided without it. Each of
   `botReactions`, `firstSuiteAt` and `botComments` is read at most once and
   its answer, or its failure, is shared: a failure makes the line of each
   named bot that needed that read `could not check` (G5 gives the
   `firstSuiteAt` exception); the other bot lines, the unnamed-bot fails
   and every other condition still print (review fix: the first draft
   folded a `botReactions` failure into one line and lost definite fails).
6. **Attributes (warn), G6.** Printed only when there is something to say.
7. `not checked: whether each finding was fixed or rejected on evidence, or
   whether a fix went beyond the findings` (the plan's scope boundary).
8. The last line: `ok <sha>` on exit 0 (unreachable in U4a), else `blocked
   <sha>: <n> failed, <m> not checked`, where `<n>` counts `fail` lines and
   `<m>` counts `could not check` and `not checked` lines; the item 7 line
   is not counted, and `unavailable` and `warn` count as neither. It is never `not ok`, which ends in
   `ok <sha>`.

## G5. Bots (R6)

- **A name matches a login** exactly, ignoring case, with or without a
  trailing `[bot]`, on both sides. **A review, reaction or comment counts
  toward a named bot only when its account's `type` is `Bot`**; a null type
  does not count (lead's ruling, 11-12; a deliberate change from the first
  draft's "any type", so a User account holding the bot's base login cannot
  finish it). Only an account of type `Bot` can be unnamed.
- **Each named bot**, in this order:
  1. Marked unavailable: `bot "<name>": unavailable <reason>`, no failure.
     Its signals are not read.
  2. A review whose `commitId` is `<sha>` with a non-empty trimmed body:
     `bot "<name>": pass finished on <sha> (review)`. An empty review is the
     start marker one connector leaves, so it is not finished.
  3. A `+1` reaction dated strictly after `firstSuiteAt(<sha>)`, the
     head's earliest check suite (KTD8); a head with no suite credits none:
     `bot "<name>": pass finished on <sha> (+1 reaction after the head's first check suite)`.
     `botReactions` is read only when a bot reaches this step, and
     `firstSuiteAt` only when the bot has a `+1` from its account, so a
     `firstSuiteAt` failure cannot hide a summary-row pass. A `botReactions`
     failure makes that bot's line `could not check`. A `firstSuiteAt`
     failure is held: a summary row (step 4) still passes, and the line reads
     `could not check` only when no summary row does.
  4. A top-level pull request comment by that bot holding a row (bodies are
     split on every line break, U+2028, U+2029 and U+0085 included) that
     contains the whole word `Completed`, contains neither `Running` nor the
     whole word `not` in any case, and whose every whole-word hex token of 7
     to 40 characters is a prefix of the head, with at least one (KTD8's
     summary row; the connector edits one comment in place):
     `bot "<name>": pass finished on <sha> (summary row)`. A row naming
     another commit as well, or reading `Running`, is not finished (review
     fix: the first draft matched `Completed` and the SHA anywhere on a line).
  5. Otherwise it fails. With a review that has a body on another commit:
     `bot "<name>": fail finished only on <commit>, not on <sha>`, naming the
     latest by `submittedAt`. With only a `+1` dated at or before the first
     suite: `bot "<name>": fail its +1 reaction is not dated after the head's
     first check suite`. Else: `bot "<name>": fail not finished on <sha>`.
     A null `commitId` names no head.
- **An unnamed bot** with any review on the pull request, at any commit and
  in any state: `bot "<login>": fail left a review but was not named with
  --bot`. Comments and reactions alone, as CI or dependency bots leave,
  print nothing. `botComments` is read only for named bots, at step 4.

## G6. Attributes (the warn line)

U3's `nonTestLines` returns `attributesTouched`. U4a reads it over the pull
request's whole range, which holds every commit U4b's count can read:

1. `hasCommit(<sha>)` and `hasCommit(baseSha)`. A missing one: `attributes:
   could not check (the clone lacks <commit>; fetch it)`, exit 2 unless
   another line fails (G3 of the
   U3 gaps file asks U4 to tell the lead to fetch).
2. `mergeBase(<sha>, baseSha)`. `null`: `attributes: could not check (no
   merge-base of <sha> and <base>)`.
3. `nonTestLines(<merge-base>, <sha>, baseSha)`. When `attributesTouched` is
   true: `attributes: warn the pull request changes a .gitattributes file,
   which can change how git reads its lines`. Never a failure. False prints
   nothing. `binaryPaths` is not printed in U4a.

## G7. Failing tests to write first

Each uses a stub runner that answers gh by request path (not call order, so
the test does not pin the order of calls) and passes git to the default
runner on a temporary repository. The all-hold fixture is: an open pull
request whose head is `--head`, two passing checks, resolved threads, one
named bot with a review on the head.

1. **Never exit 0.** The all-hold fixture exits 2; the coverage line reads
   exactly `review coverage: not checked (not built yet)`; the last line starts
   `blocked `; no line starts `ok `. `--help` with `--pr` exits 2. A failing
   condition plus coverage `not checked` exits 1, never 0 or 2.
2. AE4: the live head differs from `--head`: exit 1, the head line names both.
3. A receipt whose shipped revision differs: exit 1. One with no line, two
   lines, or a value that is not 7 to 40 hex characters: exit 1. A 7-hex
   prefix of `--head`, in any case, passes. A receipt path that is a folder: exit 2,
   stdout empty.
4. gh answers a 39-character head sha, then a bad `baseSha`: each `head:
   could not check`, exit 2.
5. A closed pull request: exit 1 on the head line.
6. No checks: `ci: fail no checks reported`. A completed check with a null
   conclusion fails. A running check fails. `neutral` and `skipped` pass
   beside a `success`. All-skipped and all-neutral fail (`no check concluded
   success`). A pending legacy status fails.
7. One unresolved, outdated thread on the second page: `threads: fail 1
   unresolved`, with both pages requested.
8. A named bot with no signal: not finished. The same bot via
   `--bot-unavailable` with a reason: an `unavailable` line and exit 2, not 1.
9. A named bot whose only review with a body is on an earlier commit: fails,
   naming it. An empty review on the head: not finished.
10. An unnamed `Bot` review: fails as unnamed. An unnamed bot's comment
    alone, and an unnamed human's review: no line.
11. A 👍 dated after the head's earliest check suite: pass. One dated before
    it: fails. A head with no suites: fails. A comment by the named bot with
    a `Completed` row naming the head's short SHA: pass (summary row). The
    same row naming an earlier commit, or reading `Running`: not finished.
12. AE5: every gh call exits 1 with an authentication error. Each gh line is
    `could not check (<call>: <gh's first stderr line>)`, naming `head`,
    `checks`, `threads` and `botReviews`; the attributes line says `could not
    check (needs the live base)`; no line reads `pass`; exit 2.
13. Every condition runs: a head mismatch and a failing check together print
    both fail lines, and the threads and bot lines too.
14. A pull request commit that adds `.gitattributes`: the warn line, and exit
    2, not 1. A clone that lacks `baseSha`: `attributes: could not check`,
    naming the commit.
15. Bad arguments, each exit 2 with stdout empty: no `--pr`, `--pr owner/repo`,
    a short `--head`, no `--bindings`, `--bot-unavailable x` with no reason, one
    name to both bot flags.
16. A check name holding a line break prints on one line.
17. `--help` alone: exit 0, and stdout names every argument in G2.

## Decisions made without asking

- D1. **Exit 1 wins over exit 2** (lead's ruling, 11-12). Coverage forces a
  non-zero exit: 2 when nothing failed, 1 when a condition failed; never 0.
  The non-zero last line is `blocked <sha>: <n> failed, <m> not checked`,
  never `not ok <sha>`, which a careless match on `ok <sha>` would read as a
  pass. R7 fixes only the exit-0 last line, so this adds to it.
- D2. **The coverage line reads `(not built yet)`, not `(U4b)`** as the lead
  first set it: the portability test forbids a plan tag in a skill script's
  printed text (worker, at build). U4b replaces the line.
- D3. **The receipt's shipped revision** is read from the receipt's
  `Shipped revision:` line, the only field that holds it. A 7-to-40-hex
  prefix of `--head` passes (review fix). A missing, repeated or non-hex one
  is exit 1; an unreadable file is exit 2.
- D4. **A pull request that is not open fails R1.** The plan does not say;
  a closed pull request cannot be merged, so passing it would mislead.
- D5. **`neutral` and `skipped` pass CI only beside a `success`** (lead's
  tightening, 11-12), as GitHub's required checks treat them. All-neutral or
  all-skipped fails. Everything else, null included, fails.
- D6. **The 👍 and summary-row rules apply to every named bot.** No file in
  the repo confirms the connector's login, and the lead names the bots, so
  the rules are not tied to one login. The summary row is read as KTD8 says
  (worker review: an earlier draft left it out). Residual: a named bot that
  gives 👍 when it starts, or writes `Completed` with the SHA before it is
  done, would read finished. Each signal counts only from the bot's own
  `Bot` account (G5).
- D7. **Bindings, carried and rollout paths are parsed, not opened**: the
  command line is final now, and U4b validates what it reads.
- D8. **The attributes warn reads the whole pull request range**, since the
  count's range is U4b's.
- D9. **`--help` exits 0 only alone**, so appending it to a run never gives 0.
- D10. **The SHA pattern is copied, not exported**: U3's file stays untouched.

## Residuals accepted (lead, 11-12)

- **A draft pull request passes R1**: `head()` does not read `draft`, and
  GitHub refuses to merge a draft anyway.
- **CI cannot see a check not yet registered**: a job gated by `needs`, or
  one GitHub has not created yet, is invisible, so one green job can meet
  "at least one success".
- **A 👍 can credit a head across a reset**: a reaction is compared with the
  commit's earliest check suite, so resetting a branch to an older commit
  can credit a 👍 left on an intermediate head. A review still running at
  the push that finishes after it can also credit the new head.
- **A 7-hex summary-row prefix could be ground to collide** (about 2^28
  hashes); GitHub returns the original time for a re-added reaction, so a
  bot whose clean 👍 predates the head may never give a fresh one (fails
  closed).
- **The older scripts' one-sided realpath guard** (receipt-check,
  review-read, model-window) goes to U4b.

Two P3s from the review of 0c9aa4f and one residual from the doc review of
830f8af (11-13) also go to U4b (lead rulings):

- **The gate can exit 0 without running.** When it is imported, or invoked
  through a path where `process.argv[1]` names another file, its entry guard
  is false: it checks nothing, prints nothing and exits 0. When
  `process.argv[1]` names a missing path, importing it throws. For a gate
  this is fail-open, so U4b fixes the guard first. Nothing reads U4a's exit
  code before U6.
- **A comment's author is checked, not its last editor** (lead ruling,
  11-13). An account with write access could edit a bot's comment into a
  `Completed <head>` row, and the gate would credit the bot; `updated_at`
  is fetched but not read. That write access can edit another account's
  comment is the review's claim, **unconfirmed** against GitHub's docs. The
  connector edits its own summary comment on every push, so U4b, test-first,
  accepts an edited row only when its last editor is the same bot (GraphQL
  `editor` and `lastEditedAt`, or `userContentEdits`) and fails closed when
  the editor cannot be read.
- **The null-type ownership test is inert.** gate-sources rejects a row with
  a null type as a transport failure before the Bot-only rule is reached, so
  the test does not test that rule (the result still fails closed).
