## G2. Item 2: a summary row counts only when the bot made its last edit (S1)

**Files:** `gate-sources.mjs` (`botComments`), `merge-gate-checks.mjs` (`namedBot`),
`test/merge-gate-sources.test.ts`, `test/merge-gate.test.ts`, `README.md`.

**The write-access claim is confirmed.** GitHub's "Managing disruptive comments", section
"Editing a comment"
(https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments),
says: "Anyone with moderate access to a repository can edit comments on issues, and anyone
with write access to a repository can edit comments on discussions, pull requests, and
commits." GitHub's GraphQL reference for issues describes `editor` as "The actor who edited
the comment.", `lastEditedAt` as "The moment the editor made the last edit." and
`userContentEdits` as "A list of edits to this content." It does not say whether `editor` is
the first editor or the last, so the gate checks both fields (D2).

- **`botComments` moves from REST to GraphQL**, paginated as `threads` is:
  `pullRequest.comments(first: 100, after: $cursor)`. Each node reads
  `author { __typename login }`, `body`, `createdAt`, `lastEditedAt`,
  `editor { __typename login }` and
  `userContentEdits(first: 100) { totalCount nodes { editor { __typename login } } }`.
  `type` is `__typename`, so the Bot-only rule does not change. A missing field is a
  `TransportFailure`, which prints `could not check`.
- **A comment's summary row credits the bot only when** the comment was never edited
  (`lastEditedAt` null and `totalCount` 0), or when `editor` and every listed edit's editor are
  the bot's own `Bot` account and every edit was read (`totalCount` ≤ 100). Anything else
  credits nothing. When no other signal passes the bot, its line reads:
  `bot "<name>": fail its summary row was edited by "<login>"`, or
  `bot "<name>": fail its summary row's edits cannot all be read`.
  A failed check-suite read outranks both: when the bot left a +1 reaction and its head's
  first check suite could not be read, the line reads
  `bot "<name>": could not check (firstSuiteAt: <reason>)`, since that +1 might have passed.
  The exit is then 2, or 1 if another condition fails. A clean summary row still passes first.

**Failing tests first:** a `Completed <head7>` row by the bot, with `editor` a `User` named
`maintainer`, does not pass; it passes today. An unedited row passes. A row edited only by the
bot passes. A null editor fails closed. An `editor` that is the bot, with one listed edit by a
human, fails. 101 edits fail closed. A node without `lastEditedAt` is `could not check`. Both

## G3. Item 3: the inert null-type case (S1)

In the ownership test, the `{ login: "review-bot", type: null }` entry never reaches the
ownership branch, because `account()` (reviews and reactions) or `actor()` (comments, read
over GraphQL) turns it into a transport failure first. **It is removed
from the loop and gets its own test of what does happen.** A reaction or a comment fails on
the bot's own line, `bot "review-bot": could not check (<call>: missing or invalid type)`. A
review fails globally, `bots: could not check (botReviews: missing or invalid type)`, because
one review read serves every named bot and the unnamed-bot check. Either way the exit is 2
when nothing else fails.
The `user: null` entry stays, since it does reach the branch.

## G5. Item 4a: review-reads fixes (S2)

**Files:** `review-reads.mjs`, `test/supervision-review-reads.test.ts`, and
`review-read.mjs`'s tests. Each must-fix is reproduced first. If one does not reproduce, its
test stays and the pull request says so.

1. **A fork does not keep what it copied.** In a fork child, the records up to the fork point
   are the parent's copy. For Claude the fork point is the record replaying the parent's
   `Agent` call (`sidecar.toolUseId`). For Codex it is the child's own history start: the
   rollout's first `session_meta` carries `forked_from_id` and
   `subagent_history_start_ordinal`, and every record whose `ordinal` is below that start is
   the parent's copy. **Corrected on a real fork's rollout** (S2): this plan first named "the
   first `task_started` after the child's own `session_meta`", but that `task_started` is the
   parent's copy. A real forked rollout copies the parent's `session_meta` and `task_started`
   below the start ordinal, and its own history begins at `thread_settings_applied`, followed
   by its own `task_started`. A rollout with a `forked_from_id` whose start ordinal is missing
   or not a non-negative integer, or any of whose records lacks a valid ordinal, gives no
   records (fail closed). A rollout with no `forked_from_id` keeps the current rule and needs
   no ordinal. The copied records give no review and no triple, and the triple starts empty after
   the fork point. Test: a fresh parent's read and review, copied into its fork. The fork's
   later review has no read, and the copied review is not returned for the fork.
   **Freshness comes from the parent chain: a fork carries its starter's context** (KTD8,
   narrowed by lead ruling (4)). A fork reached as a walked child of a fresh thread reads as
   fresh. That includes a caller-named forked rollout listed beside its fresh caller-named
   parent, which is read inside that parent's walk. A caller-named forked rollout read on its
   own, with no fresh parent walking it, is never credited, whatever the cutoff keeps. A fork
   of the main session or of any non-fresh thread is not fresh. A caller-named rollout read on
   its own is fresh only as one `codex exec` run: a
   `session_meta` with source `exec`, no `forked_from_id`, and one `task_started`. A fork fails
   all three. Its source is `{subagent: {thread_spawn: …}}`, it carries `forked_from_id`, and
   it holds two `task_started` records, the copied one and its own. **A walked fork is read as
   `transcript-uses.mjs`'s `codexContext` reads it** (narrowed in S2, lead ruling (4)): a fork
   reached as a child of a fresh starter inherits that freshness, and a fork whose starter
   chain reaches no fresh thread (the main session, or a forked caller-named rollout) is not
   fresh, down to a grandchild. The cutoff only keeps the parent's copied records from being
   attributed to the child. For Claude, a fork sidecar with no `toolUseId`, or one that no
   replayed `Agent` call matches, gives no records (fail closed).
2. **A read counts only once its result has landed.** The triple is set when the
   `tool_result` record is reached in file order, not at the `tool_use`. Test: a Bash read and
   a Skill call in one assistant message, with the read's result after the Skill call. The
   review has no read.
3. **Closes residual (b).** `HEX_TOKEN` becomes `\b[0-9a-f]{7,}\b`, so a hex run longer than 40
   is a token that no base starts with, and `baseNamed` reads false. Test:
   `base:<sha> <41 hex>` reads false.
4. **Each record carries `thread`**, the resolved path of its transcript. `readReviewReads`
   de-duplicates records by thread, time, skill and args (`uniqueReviews`). When duplicates
   disagree, the not-fresh one survives (fail closed), so the survivor does not depend on rollout order
   (S2 review). It orders them by `Date.parse(at)`, never by position in the array; records
   with no time that parses follow the timed ones, in traversal order. Such a record is not
   credited (`no time recorded`), but that rejection belongs to the coverage check (G7, S3),
   not to S2. A `tool_result` counts only in a `user` record. Test: two named rollouts that
   reach each other give one record per call, the not-fresh one, in either order.
5. **The untested U1 cases:** `parseArgs` with a flag given twice, or with an empty value;
   `--from` an orphan commit, which has no merge-base (exit 1); and a rollout path that is a
   folder, which makes `readReviewReads` rethrow `EISDIR`.

## G6. Item 4b: the 150-line count (S2)

**Files:** `gate-sources.mjs` (`nonTestLines`, `textLineCount`), `merge-gate-checks.mjs`,
`test/merge-gate-sources.test.ts`, `test/merge-gate.test.ts` and `README.md`. The count stays
KTD5's per-commit sum, as U3 built it, and is never the net diff.

- **Binary rows are re-counted as text.** This is a deliberate change from KTD5, which skips
  them. Each non-test row whose numstat reads `-` is re-counted once: the same commit's diff
  arguments, plus `--text`, for that one path. `binaryPaths` still lists them. The rename
  recount always passes `--text`. A row whose rename was already re-counted is not re-counted
  again, keyed by commit and path.
- **A move counts by which side of the test boundary each path is on** (S2 review, lead
  ruling (a)). A move between two non-test paths, or between two test paths, counts only its
  changes, so a pure move (R100) counts 0 non-test lines, binary or text. A binary move
  between non-test paths is re-counted as that one rename, with `--text`, so it counts its
  changed lines and never the whole file. A move from a test path to a non-test path counts
  the whole destination file, binary or text; a move from a non-test path into a test path
  counts the whole old file. Checked in S2: a text pure move from `test/` to `src/` did not
  dodge the count before this fix (it counted the whole file). The bug was the binary pure
  move between source paths, which counted the whole file instead of 0.
- The gate prints a `binary paths: warn` line whenever `binaryPaths` is not empty. Non-test
  paths go in `counted as text: "<path>", "<path>"`. Test paths get their own clause,
  `test paths, not counted: "<path>"`, after a `; ` when both appear, or alone. A binary move
  from a non-test path into a test path lists its new path in that clause. Its old path is
  re-counted in full and git still reads it as binary, so it shows under `counted as text`:
  `counted as text: "src/a.bin"; test paths, not counted: "test/a.bin"`. It is never a
  failure.

**Failing tests first:** a `.gitattributes` holding `src/*.mjs -diff`, with a 300-line `.mjs`
file, counts 300. A 300-line non-test file with a NUL in its first 8000 bytes counts 300. A NUL
file renamed from `test/` to `src/` counts once. A binary file under `test/` counts 0. A pure
move counts 0 between source paths and the whole file from `test/` to `src/`, binary or text. **The
net-versus-sum fixture:** three commits whose edits to one file overlap, net 29 and sum 37,
count 37. A merge resolved by hand counts its remerge lines.

## G7. Item 4c: R3 and R4 coverage (S3)

**Files:** `merge-gate-checks.mjs`; `review-coverage.mjs` (new: the decision logic, pure over
records and a sources object); `test/merge-gate.test.ts`, with fixtures under
`test/fixtures/supervision/merge-gate/`; `README.md`.

**Inputs.** Each `--bindings` file is read as JSON before any process runs. If it cannot be
read, or its `skill` is neither `story-worker` nor `project-lead`, the gate prints
`merge-gate: --bindings <path> is not a worker's or a lead's bindings file` and exits 2. The
review performers are the `native_id`s bound to `review` and `doc-review` in a worker's file,
and to `review-before-merge` in a lead's. `readReviewReads` runs over each file's transcripts,
with those skills, and over the `--codex-rollout` paths. A `missing` entry prints
`review: could not check (<path> not found)`, unless G8 covers it.

**A record is creditable only when all of these hold.** Each failed condition gives the reason
in parentheses:

- it is fresh (`not fresh`), and its `outcome` is ran (`did not run`);
- it has a triple (`no read recorded`) from a clean tree (`dirty tree`);
- `baseNamed` is true, or a Codex use meets G10 (`base not named`);
- its time parses (`no time recorded`);
- its performer is bound, and not by fallback (`bound by fallback`). A namespaced call matches
  only the binding's exact `native_id`, and a bare one (a Codex skill read) its unqualified
  name, as `matches` in `operation-state.mjs` reads a skill call; a call no binding matches is
  not a review record. A by-fallback operation still matches its suggested names unqualified,
  which credits nothing either way;
- `read.script` is an absolute path to a trusted `review-read.mjs`, compared by realpath
  (`read by another script`). A relative script path fails closed: Node resolves it against
  the reviewer's working directory, and the read record holds no working directory, only
  `script`, `checkout` and `from`; resolving it against `--checkout` would judge a file that
  may not be the one that ran (11-15 ruling 4). Trusted copies are the gate's own sibling and
  the one in the `supervision-setup` folder beside each bindings file's table path. A relative
  table path is resolved against `--checkout`. This catches a wrong or stale read script, not
  forgery: transcripts and carried output can be forged (KTD11, plan:118).

**Full or re-check (KTD4).** Let `M = mergeBase(head, baseSha)`; the chain is
`firstParentChain(M, head)`. A record is full when its base equals
`mergeBase(record.head, baseSha)` and it is not a `--codex-rollout` run (KTD8). Otherwise it is
a re-check. A reviewed commit missing from the clone credits nothing:
`reviewed commit <sha> is not in the clone`.

**How a `--codex-rollout` run is recognised.** Records carry `thread`, `place` and `session`,
nothing that names the rollout they came from. A record is a `--codex-rollout` run when its
`thread` is a named rollout's own path, or its `session` is the id of a named rollout that
`readReviewReads` read as its own reviewer. It returns those ids as `rollouts`, and every
record of that walk carries the id as `session`, its walked children's included. A named
rollout that a listed transcript reaches is read in that transcript's walk instead: its own
thread is still a run, and its children keep the listed session. **Every descendant of a named
rollout is a re-check, never the full review** (11-15 ruling 3, fail closed under KTD8),
including the children of a named rollout that a listed transcript reaches; today's tag misses
that last case, since those children carry the listed session. In S3 no Codex record reaches
this rule, since each one fails `base not named` until G10, so S3 tests `rollouts` in
`review-reads`, and S4 implements the descendant rule and tests it at the gate (G10).

**Where a record sits on the chain (the G7 placement rule, lead rulings 1 and 2; 11-15
ruling 1).** With `M` the merge-base and `patchId(x, y)` the `git patch-id --verbatim` of the
cumulative diff `x..y`, a record `r` sits (i) at `r.head` when that is a first-parent chain
commit; (ii) for a worker's `r` whose head is an ancestor of the final head but not on the
chain, at the first chain commit `c` with `patchId(M, c)` equal to `patchId(M, r.head)`, the
same patch; (iii) for a worker's full review whose head is not an ancestor of the final head,
by KTD7, at the first chain commit `c` with `patchId(M, c)` equal to
`patchId(mergeBase(r.head, baseSha), r.head)`. (iv) A full review whose head is `M` or an
ancestor of it reads `M..M`, nothing, and credits nothing: `reads nothing`; a re-check there
sits at `M`, where it can move no frontier. No patch-id credit goes to a re-check whose head is
not an ancestor of the final head (KTD7, plan:114) or to any lead record (lead ruling 2).
Otherwise `r` credits nothing: an ancestor head with no patch match, or a lead record there,
gives `only on a merged side branch`; a head off the final head's history with no match, a
re-check there, or a lead record there gives `not on the head's history`; a reviewed commit
missing from the clone gives `reviewed commit <sha> is not in the clone`.

**This narrows KTD4's eligibility** ("whose head is an ancestor of the final head, or
patch-equivalent to one", plan:111) and this file's earlier placement rule, which let a full
review sit at the first chain commit containing its head: a full review only on a merged side
branch would start the chain at the merge and leave the mainline commits beside it uncovered.
Re-checks are narrowed the same way.

**R3 line.** The start is the full record furthest along the chain, ties going to the later
call.
- `review: pass full review read <c>`, adding ` (patch-id match of <r.head>)` when the start
  sits by patch-id, under KTD7 or on a side branch.
- `review: fail no creditable full review of <head> (<n> review calls, none credited: <reason>, <reason>)`,
  with each distinct reason listed once.

**R4 line.** From the start, a re-check moves the covered frontier `f` to its own place when

nothing moves `f`. **Open fail-open, owned by S4** (11-15 ruling 5): a base that is only an
ancestor of `f` lets coverage pass over content no diff showed (G10). A clean merge from the base branch counts as covered: it has two parents,
the second is an ancestor of `baseSha`, and it is not in `nonTestLines(...).merges`. The line
count is `nonTestLines(start, head, baseSha).total` (G6).
- `coverage: pass <start>..<head> covered by <k> re-checks; <n> non-test lines since the full review`.
- `coverage: fail uncovered commits <sha>, <sha>`, or
  `coverage: fail <n> non-test lines since the full review at <start>, 150 or more: a full review must come again`.
  When both apply, one line holds both reasons, joined by `; `.
- `coverage: fail no full review to start from`, when R3 found none.

**Failing tests first, AE1 first** (the plan's execution note): AE1, AE2 and AE3 (G12). Also:

- D6: a worker's full review whose head is only on a merged side branch, with no patch match,
  credits nothing. Beside a mainline full review, a re-check of the merge covers it. A worker's
  side-branch full review patch-equal to a chain commit sits at that commit; a lead's does not.
- G7(ii): a worker's re-check off the head's history, patch-equal to a chain commit, gets no
  patch-id credit. A full review at the merge-base reads nothing (11-15 ruling 1).
- Re-checks A..B and C..D leave B..C uncovered, and the line names its commits. Overlapping
  re-checks pass.
- A re-check whose args name A, while its read recorded the merge-base, credits nothing.
- A clean base merge after the full review passes, counting 0 lines.
- The lead's `review-before-merge` of the final head passes R3 on its own. A lead record whose

## G8. Item 4d: carried evidence, R8 and KTD11 (S3)

`--carried <path>` is a handoff, read with `readHandoff`. Its `used` lines for `review` or
`doc-review` that carry `read <head> from <base>` become carried records, with their args.
One that says `(dirty tree)` is dirty. They count only for a missing transcript, listed or a
Codex child a listed one started, whose id is in the section's `covered` set (its `transcript
<id>:` lines, plus each used line's subagent), and each is matched only against the bindings
of the worker whose transcripts list its session.

**A carried record can be the start or a link only when the lead's own creditable
`review-before-merge` record reads a non-empty range ending at `head`** (11-15 ruling 2). When one is used, the R3 or R4 verdict is
`carried`, which counts as neither failed nor unchecked, and the line ends
` (carried; the lead reviewed <head>)`. Without the lead's record, the line reads
`review: fail carried evidence needs the lead's own review of <head>` when no full review is
credited and a carried full record would otherwise start the chain. A missing transcript whose

## G9. Item 4e: the doc-review condition (S4)

**This is a deliberate change from KTD6.** A doc path is any changed path ending in `.md`, in
any case, skill text and instruction files included. Every doc path changed in `M..head` needs
a creditable `doc-review` record that names it. That record's head must come after the path's
last change: either `head` itself, or an ancestor of `head` with no later commit touching the
path. "Names it" means the repo-relative path appears whole in the call's args, bounded by the
start, the end, a blank, a quote or a comma. This adds to R3; it does not replace it.

KTD6's docs-only rule stays (D7). A pull request is docs-only when every path is markdown and
none is an agent surface, ignoring a version-only manifest change. On such a pull request, a
doc review can serve as R3's full review.
- `doc review: pass no doc path changed`, or `doc review: pass <n> doc paths reviewed after their last change`.
- `doc review: fail not reviewed after their last change: "<path>", "<path>"`.

Tests:
- A mixed diff with only a code review fails on the doc line.
- A doc review naming both changed files passes. One that names one of the two fails, naming
  the other.
- A doc changed after its review fails.
- A docs-only pull request with a doc review passes R3. A later `skills/` code path makes R3
  need the code review.
- A version-only manifest change keeps a pull request docs-only.

## G10. Item 4f: Codex-hosted skill reviews (S4)
