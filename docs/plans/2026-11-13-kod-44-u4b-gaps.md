## G1. Item 1: no entry point exits 0 without running (S1)

**Files:** `skills/supervision-setup/scripts/merge-gate.mjs` (becomes the entry),
`merge-gate-checks.mjs` (new: today's file moved with `git mv`, less its guard), `entry.mjs`

- **`merge-gate.mjs` runs on every load, with no guard.** It imports `main` from
  `merge-gate-checks.mjs` and sets `process.exitCode = main(process.argv.slice(2))`. When a
  wrapper imports it, it runs on the wrapper's argv, which gives a gate run or an exit-2
  argument error. No argv shape, symlink, node version or importer can make it exit 0 without
  running. Tests import `main` from `merge-gate-checks.mjs`.
- **The three older scripts guard with `isEntry(import.meta)`** from `entry.mjs`. It returns
  `meta.main` where node sets it (24.2 and later). Otherwise it compares the realpaths of both
  `process.argv[1]` and the module. A realpath error reads as "not the entry", so a missing
  path no longer throws at import.
- **For the later unit:** stdout's last line is `ok <head>` only on exit 0 from a pull-request
  check. Bad arguments and the import case print nothing on stdout, and `--help` prints usage
  with no `ok` line. A lead that requires exit 0 *and* a last line equal to `ok <its --head>`
  rejects every path that did not check.
- **The install-shape test** imports every script except `merge-gate.mjs`. It then spawns
  `merge-gate.mjs` with no arguments and asserts exit 2, the `merge-gate: ` usage on stderr and
  empty stdout. The assertion is updated, not weakened.

**Failing tests first**, each spawned with `process.execPath`:

## G2. Item 2: a summary row counts only when the bot made its last edit (S1)

**Files:** `gate-sources.mjs` (`botComments`), `merge-gate-checks.mjs` (`namedBot`),
`test/merge-gate-sources.test.ts`, `test/merge-gate.test.ts`, `README.md`.

**The write-access claim is confirmed.** GitHub's "Managing disruptive comments", section
"Editing a comment"
(https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments),
says: "Anyone with moderate access to a repository can edit comments on issues, and anyone
with write access to a repository can edit comments on discussions, pull requests, and
commits." GitHub's GraphQL reference for issues describes `editor` as "The actor who edited
the comment.", `lastEditedAt` as "The moment the editor made the last edit." and
`userContentEdits` as "A list of edits to this content." It does not say whether `editor` is
the first editor or the last, so the gate checks both fields (D2).

- **`botComments` moves from REST to GraphQL**, paginated as `threads` is:
  `pullRequest.comments(first: 100, after: $cursor)`. Each node reads
  `author { __typename login }`, `body`, `createdAt`, `lastEditedAt`,
  `editor { __typename login }` and
  `userContentEdits(first: 100) { totalCount nodes { editor { __typename login } } }`.
  `type` is `__typename`, so the Bot-only rule does not change. A missing field is a
  `TransportFailure`, which prints `could not check`.
- **A comment's summary row credits the bot only when** the comment was never edited
  (`lastEditedAt` null and `totalCount` 0), or when `editor` and every listed edit's editor are
  the bot's own `Bot` account and every edit was read (`totalCount` ≤ 100). Anything else
  credits nothing. When no other signal passes the bot, its line reads:
  `bot "<name>": fail its summary row was edited by "<login>"`, or
  `bot "<name>": fail its summary row's edits cannot all be read`.

**Failing tests first:** a `Completed <head7>` row by the bot, with `editor` a `User` named
`maintainer`, does not pass; it passes today. An unedited row passes. A row edited only by the
bot passes. A null editor fails closed. An `editor` that is the bot, with one listed edit by a
human, fails. 101 edits fail closed. A node without `lastEditedAt` is `could not check`. Both
pages of a two-page answer are read.

## G5. Item 4a: review-reads fixes (S2)

**Files:** `review-reads.mjs`, `test/supervision-review-reads.test.ts`, and
`review-read.mjs`'s tests. Each must-fix is reproduced first. If one does not reproduce, its
test stays and the pull request says so.

1. **A fork does not keep what it copied.** In a fork child, the records up to the fork point
   are the parent's copy. For Claude the fork point is the record replaying the parent's
   `Agent` call (`sidecar.toolUseId`); for Codex it is the first `task_started` after the
   child's own `session_meta`. Confirm both on a real fork's transcript before fixing. The
   copied records give no review and no triple, and the triple starts empty after the fork
   point. Test: a fresh parent's read and review, copied into its fork. The fork's later review

   `tool_result` record is reached in file order, not at the `tool_use`. Test: a Bash read and
   a Skill call in one assistant message, with the read's result after the Skill call. The
   review has no read.
3. **Closes residual (b).** `HEX_TOKEN` becomes `\b[0-9a-f]{7,}\b`, so a hex run longer than 40
   is a token that no base starts with, and `baseNamed` reads false. Test:
   `base:<sha> <41 hex>` reads false.
4. **Each record carries `thread`**, the resolved path of its transcript. The gate
   de-duplicates records by thread, time, skill and args. It orders them by `Date.parse(at)`,

   (`no time recorded`). Test: two named rollouts that reach each other give one record per

## G7. Item 4c: R3 and R4 coverage (S3)

**Files:** `merge-gate-checks.mjs`; `review-coverage.mjs` (new: the decision logic, pure over
records and a sources object); `test/merge-gate.test.ts`, with fixtures under
`test/fixtures/supervision/merge-gate/`; `README.md`.

**Inputs.** Each `--bindings` file is read as JSON before any process runs. If it cannot be
read, or its `skill` is neither `story-worker` nor `project-lead`, the gate prints
`merge-gate: --bindings <path> is not a worker's or a lead's bindings file` and exits 2. The
review performers are the `native_id`s bound to `review` and `doc-review` in a worker's file,
and to `review-before-merge` in a lead's. `readReviewReads` runs over each file's transcripts,
with those skills, and over the `--codex-rollout` paths. A `missing` entry prints
`review: could not check (<path> not found)`, unless G8 covers it.

**A record is creditable only when all of these hold.** Each failed condition gives the reason
in parentheses:

- it is fresh (`not fresh`), and its `outcome` is ran (`did not run`);
- it has a triple (`no read recorded`) from a clean tree (`dirty tree`);
- `baseNamed` is true, or a Codex use meets G10 (`base not named`);
- its time parses (`no time recorded`);
- its performer is bound, and not by fallback (`bound by fallback`);
- `read.script` resolves to a trusted `review-read.mjs` (`read by another script`). A relative
  script path is resolved against `read.checkout`, then compared by realpath. Trusted copies
  are the gate's own sibling and the one in the `supervision-setup` folder beside each
  bindings file's table path. A relative table path is resolved against `--checkout`.

**Full or re-check (KTD4).** Let `M = mergeBase(head, baseSha)`; the chain is
`firstParentChain(M, head)`. A record is full when its base equals
`mergeBase(record.head, baseSha)` and it is not a `--codex-rollout` run (KTD8). Otherwise it is
a re-check. A reviewed commit missing from the clone credits nothing:
`reviewed commit <sha> is not in the clone`.

**Where a record sits on the chain.** If its head is an ancestor of `head`, the record sits at
the last chain commit that contains it. A full record whose head is not an ancestor can still
be credited by KTD7. Its `patchId(mergeBase(r.head, baseSha), r.head)` must equal
`patchId(M, c)` for some chain commit `c`, and it then sits at `c`. With no match, the reason
is `not on the head's history`. A re-check never gets patch-id credit.

**R3 line.** The start is the full record latest on the chain.
- `review: pass full review read <c>`, adding ` (patch-id match of <r.head>)` under KTD7.
- `review: fail no creditable full review of <head> (<n> review calls, none credited: <reason>, <reason>)`,
  with each distinct reason listed once.

**R4 line.** From the start, a re-check moves the covered frontier `f` to its own place when
its base is `f` or an ancestor of `f` and its place is later on the chain. This repeats until
nothing moves `f`. A clean merge from the base branch counts as covered: it has two parents,
the second is an ancestor of `baseSha`, and it is not in `nonTestLines(...).merges`. The line
count is `nonTestLines(start, head, baseSha).total` (G6).
- `coverage: pass <start>..<head> covered by <k> re-checks; <n> non-test lines since the full review`.
- `coverage: fail uncovered commits <sha>, <sha>`, or
  `coverage: fail <n> non-test lines since the full review at <start>, 150 or more: a full review must come again`.
  When both apply, one line holds both reasons, joined by `; `.
- `coverage: fail no full review to start from`, when R3 found none.

**Failing tests first, AE1 first** (the plan's execution note): AE1, AE2 and AE3 (G12). Also:
- A review that ran only in a fork fails R3, and so does one that read a dirty tree.
- Re-checks A..B and C..D leave B..C uncovered, and the line names its commits. Overlapping
  re-checks pass.
- A re-check whose args name A, while its read recorded the merge-base, credits nothing.
- A clean base merge after the full review passes, counting 0 lines.
- The lead's `review-before-merge` of the final head passes R3 on its own. A lead record whose
  head is not an ancestor of the head does not count.
- A rebase before the push with an equal patch-id is credited. One that differs only in
  indentation is not. A reviewed commit absent from the clone fails, and the line says so.
- `review` bound by fallback fails. A `--codex-rollout` run from the merge-base, with no other
  review, fails R3.
- A read by a `review-read.mjs` copied elsewhere fails. Records out of array order are judged
  by time.

## G8. Item 4d: carried evidence, R8 and KTD11 (S3)

`--carried <path>` is a handoff, read with `readHandoff`. Its `used` lines for `review` or
`doc-review` that carry `read <head> from <base>` become carried records, with their args.
One that says `(dirty tree)` is dirty. They count only for a listed transcript that is missing
and that the section covers, by the receipt check's `covered` rule.

**A carried record can be the start or a link only when the lead's own creditable
`review-before-merge` record reads `head`.** When one is used, the R3 or R4 verdict is
`carried`, which counts as neither failed nor unchecked, and the line ends
` (carried; the lead reviewed <head>)`. Without the lead's record, the line reads
`review: fail carried evidence needs the lead's own review of <head>`. A missing transcript
that no carried line covers prints `could not check` and exits 2.

Tests: both AE6 cases (G12). Carried lines are ignored when the local transcript can be read.
A carried dirty read credits nothing.

## G9. Item 4e: the doc-review condition (S4)

**This is a deliberate change from KTD6.** A doc path is any changed path ending in `.md`, in
any case, skill text and instruction files included. Every doc path changed in `M..head` needs
a creditable `doc-review` record that names it. That record's head must come after the path's
last change: either `head` itself, or an ancestor of `head` with no later commit touching the
path. "Names it" means the repo-relative path appears whole in the call's args, bounded by the
start, the end, a blank, a quote or a comma. This adds to R3; it does not replace it.

KTD6's docs-only rule stays (D7). A pull request is docs-only when every path is markdown and
none is an agent surface, ignoring a version-only manifest change. On such a pull request, a
doc review can serve as R3's full review.
- `doc review: pass no doc path changed`, or `doc review: pass <n> doc paths reviewed after their last change`.
- `doc review: fail not reviewed after their last change: "<path>", "<path>"`.

Tests:
- A mixed diff with only a code review fails on the doc line.
- A doc review naming both changed files passes. One that names one of the two fails, naming
  the other.
- A doc changed after its review fails.
- A docs-only pull request with a doc review passes R3. A later `skills/` code path makes R3
  need the code review.
- A version-only manifest change keeps a pull request docs-only.

## G10. Item 4f: Codex-hosted skill reviews (S4)

**This is a deliberate change from KTD3 and KTD6.** A Codex skill use takes no args, so it is
credited on its read record alone, when all of these hold:
- its tree is clean;
- its read is the last one before the use in the same rollout, and no other read ran between
  them, failed or not;
- its base is `mergeBase(r.head, baseSha)` for a full review, or exactly the covered
  frontier's head for a re-check.

For doc credit, each doc path it covers changed in `base..r.head`, and not after it. A
`--codex-rollout` run stays a re-check only (KTD8).

Tests, one for each condition: a valid full review; a valid re-check; a dirty tree; a base
that is neither; a failed read between the read and the use; a read only after the use; a doc
path outside the read's range.

## Decisions made without asking

- D1. **The gate's entry has no guard.** A guard cannot tell an importer that expects a run
  from a test that does not. Only the split makes "never exit 0 without running" hold by
  construction. The older scripts keep a guard (G1), with realpath on both sides, as the
  lead asked.
- D2. **A summary row needs both `editor` and every listed edit to be the bot,** because the
  docs do not say which editor `editor` names. A human edit that the bot later overwrote still
  fails closed.
- D3. **The null-type case is asserted as `could not check`,** not deleted silently.
- D4. **Coverage prints three lines,** `review:`, `coverage:` and `doc review:`, in place of
  U4a's one. The later unit reads these three names.
- D5. **The read script is trusted by realpath** against the gate's own copy and each bindings
  file's `supervision-setup` copy, as the lead's notes ask.
- D6. **A re-check sits on the first-parent chain**, at the last chain commit that contains
  its head. A head found only on a merged side branch sits at its merge.
- D7. **KTD6's docs-only path stays beside G9.** The lead's "as well as the code review" is
  read as applying to a mixed diff. Flip it if a code review is meant for every pull request.
- D8. **Of the U1 residuals, U4b closes (b) only.** (c) has no reliable marker for a continued
  Claude subagent, so it goes on the shadow watch. (e) is a traversal refactor shared with the
  receipt check and outside this unit's size. G5's de-dup removes its symptom at the gate.
- D9. **Bots are named by login, with no alias table.** An alias would tie a portable script to
  one vendor.
- D10. **If S3 goes past 300 non-test lines, G8 moves to S4.** S3 still cannot print `ok`.
