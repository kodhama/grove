## G1. The runner and the failure

- **The runner** is `run(cmd, args, { cwd, input, env }) → { status, stdout,
  stderr, error }`, the shape `spawnSync` returns. The default is a
  synchronous `spawnSync` with `encoding: "utf8"` and a 64 MiB `maxBuffer`,
  as `review-read.mjs` sets them, plus a 30-second timeout of its own. A
  call may ask for raw bytes instead (`encoding: "buffer"`): the diff that
  feeds `git patch-id` is read and passed on as bytes, so a non-UTF-8 byte
  is never replaced before it is hashed. Never a shell: an argv array only.
- **Git runs in one checkout, with its output pinned.** The checkout path is
  resolved to an absolute path once, and git runs only by `-C <that path>`.
  `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` are cleared, as
  `review-read.mjs` does, and so are `GIT_DIFF_OPTS` and `GIT_EXTERNAL_DIFF`.
  Every git call carries `-c` overrides for each setting found to change what
  is parsed: `diff.algorithm`, `diff.renames`, `diff.noprefix`,
  `diff.mnemonicPrefix`, `diff.relative`, `diff.context`,
  `diff.interHunkContext`, `diff.indentHeuristic`, `diff.suppressBlankEmpty`,
  `diff.renameLimit`, `merge.renameLimit`, `diff.ignoreSubmodules`,
  `diff.submodule`, `color.ui`, `log.showSignature`, `merge.conflictStyle`,
  `core.quotePath` and `core.attributesFile`. That list is what review
  found, not every setting git has. The diff-producing calls also pass
  `--no-ext-diff`, `--no-textconv` and `--ignore-submodules=none`, and end
  their revisions with `--`, so a revision is never read as a path.
- **Attributes come from the checkout's work tree**, not from a commit:
  git reads the checked-out `.gitattributes` and `.git/info/attributes`
  (`core.attributesFile` is pinned to `/dev/null`, so no global file
  applies). When the lead's clone has the pull request checked out, the pull
  request's own `.gitattributes` applies to every read. `--no-textconv`
  stops a textconv driver, but a `-diff` or a `merge=` attribute still
  shapes a count. Git 2.39 has no `--attr-source`, so this is not engineered
  out; see G8.
- **The failure is thrown, never returned.** `gate-sources.mjs` exports a
  `TransportFailure` error class with `call` (the source function's name,
  such as `checks` or `patchId`) and `reason` (one line). Its message is
  `<call>: <reason>`. A thrown failure cannot be read as a value by mistake,
  so a missing field can never pass (KTD9). U4 maps it to exit 2.
- **What is a transport failure:** the runner's `error` (not found, timed
  out), a non-zero exit where the call defines no answer for it, stdout that
  is not JSON where JSON is expected, a field the answer needs that is
  missing or of the wrong type, a page cap reached (G2), and a revision that
  is empty or starts with `-`, refused before any process runs.

## G2. Each gh call

Every call is a single `gh api` request. **The module paginates itself**, so
a stub can return the pages one by one and a test can see both pages read.
`gh --paginate` is not used. The cap is 50 pages per endpoint, so `checks`,
which reads two endpoints, can read 100; reaching a cap is a transport
failure. `gh` exiting non-zero, unauthenticated included, is a transport
failure carrying the call's name and gh's first stderr line.

| Answer | Request | Pages end when | Fields read |
| --- | --- | --- | --- |
| `head` | `repos/{o}/{r}/pulls/{n}` | one request | `head.sha`, `base.ref`, `base.sha`, `state` |
| `checks` | `repos/{o}/{r}/commits/{sha}/check-runs?per_page=100&page={p}` and `repos/{o}/{r}/commits/{sha}/status?per_page=100&page={p}` | a page shorter than 100 | check runs: `name`, `status`, `conclusion`; statuses: `context`, `state` |
| `firstSuiteAt` | `repos/{o}/{r}/commits/{sha}/check-suites?per_page=100&page={p}` | a page shorter than 100 | `created_at`; the answer is the earliest, or `null` with no suites |
| `threads` | GraphQL `repository.pullRequest.reviewThreads(first: 100, after: $cursor)` | `pageInfo.hasNextPage` false | `id`, `isResolved`, `isOutdated`, `path`, the first comment's `author.login` |
| `botReviews` | `repos/{o}/{r}/pulls/{n}/reviews?per_page=100&page={p}` | a page shorter than 100 | `user.login`, `user.type`, `commit_id`, `body`, `state`, `submitted_at` |
| `botComments` | `repos/{o}/{r}/issues/{n}/comments?per_page=100&page={p}` | a page shorter than 100 | `user.login`, `user.type`, `body`, `created_at`, `updated_at` |
| `botReactions` | `repos/{o}/{r}/issues/{n}/reactions?per_page=100&page={p}` | a page shorter than 100 | `user.login`, `user.type`, `content`, `created_at` |

- **A check is reported as it stands.** A check run carries `completed:
  status === "completed"` and its conclusion only when completed; a running
  check's empty conclusion is never read as a result. A legacy status is
  completed unless its `state` is `pending`. U4 decides what passes.
- **What GitHub may null is a value.** GitHub's REST schema lets a review's
  `commit_id` be null (its commit was force-pushed away), a review's
  `submitted_at` be absent (a pending review), and a row's `user` be null (a
  deleted account). Those read as `null`; a null names no head, so it can
  never satisfy U4. A thread's deleted author reads as a null `authorLogin`
  in the same way. A check run's `conclusion` is null until it completes,
  and is read only then. Every other field the table names is required.
- **The answers are normalised, camel-cased records**, one array per answer,
  every page concatenated in the order received. U3 judges nothing: which
  bot is named, which signal finishes it and whether a thread blocks are U4's.
  `head`'s `baseSha` is GitHub's own base commit, so U4 need not trust a
  local base ref that may be stale.

## G3. Each git call, and the answers that are not failures

| Answer | Command | Not a failure |
| --- | --- | --- |
| `hasCommit(sha)` | `git rev-parse --verify --quiet <sha>^{commit}` | exit 1: `false`. Any other non-zero exit, such as a checkout that is not a repository, is a transport failure |
| `isAncestor(a, b)` | `git merge-base --is-ancestor <a> <b>` | exit 1: `false` |
| `mergeBase(a, b)` | `git merge-base <a> <b>` | exit 1 with empty stdout: `null` |
| `firstParentChain(from, to)` | `git rev-list --first-parent --reverse --parents <from>..<to> --` | none; each entry is `{ sha, parents }`, a merge has two or more |
| `numstat(from, to)` | `git log <diff flags> --first-parent --no-merges --numstat -z --format=commit:%H <from>..<to> --` | none |
| `remergeNumstat(merge)` | `git show <diff flags> --remerge-diff --format= --numstat -z <merge> --` | empty output: no rows. `nonTestLines` reads it as a clean merge only when the same remerge-diff, read as a patch, has no `remerge CONFLICT` notice without a row |
| `patchId(base, head)` | `git diff <diff flags> --binary --src-prefix=a/ --dst-prefix=b/ <base> <head> --`, read as bytes and piped as `input` to `git patch-id --verbatim` | an empty diff: `null` |

`<diff flags>` is `--no-ext-diff --no-textconv --no-color
--ignore-submodules=none -M`, one constant in the module, after the `-c`
overrides of G1.

- **Only `hasCommit` answers for an absent commit.** `isAncestor`,
  `mergeBase`, `patchId` and the range calls exit 128 on a commit the clone
  lacks, which is a transport failure. KTD7 needs a reviewed commit missing
  from the clone to fail as evidence (exit 1), so U4 asks `hasCommit` of every
  reviewed head before any other git call on it. The same holds for `head`'s
  `baseSha`: a clone that has not fetched it exits 128 on the first range
  call, so U4 asks `hasCommit(baseSha)` first and tells the lead to fetch.
- **A null patch-id matches nothing.** `patchId` answers `null` for an empty
  diff; U4 must never treat two nulls as equal.
- **Numstat is read NUL-delimited** (`-z`), so a path is taken as git wrote
  it: no quoting to undo, and a literal ` => ` in a file name is not read as
  a rename. A rename row carries both paths, and it counts under the new one.
  `--binary` makes two diffs that differ only in a binary file's content give
  different patch-ids.
- **The line count** (KTD5): `nonTestLines(from, to, base)` sums added plus
  deleted over each non-merge first-parent commit's `numstat`, skipping
  binary rows (`-`) and every path the test pattern matches (G4). A
  two-parent first-parent merge whose second parent is `base` or one of its
  ancestors is a merge from the base branch: it counts its `remergeNumstat`
  lines, zero for a clean one. A merge with more than two parents is never
  from the base branch. Any other merge counts `git diff --numstat` from its
  first parent to the merge, under the same skips and pinning. The answer is
  the total, the per-commit counts, the merges (every merge not from the base
  branch, and every base-branch merge with a non-empty remerge diff), which
  need a re-check of their own (U4), `binaryPaths` and `attributesTouched`.
- **A hidden conflict is not clean.** Under a `merge=binary` attribute a
  remerge can conflict, take one side, and match the merge commit, so its
  numstat has no row. A base-branch merge whose remerge-diff carries a
  `remerge CONFLICT` notice for a path with no numstat row counts as a merge
  not from the base branch: its first-parent diff, listed. So does one whose
  notice cannot be tied to a path. A conflict whose resolution shows as rows
  still counts only those rows (KTD5).
- **A rename out of the tests counts in full.** A rename row keeps its old
  path. When the old path is a test path and the new one is not, the row
  counts the new file's lines from the same diff re-run with `--no-renames`
  for that one path (a literal pathspec), so moving a tested file into
  `src/` is not a free change.
- **A rename into the tests counts the old file.** When the old path is not
  a test path and the new one is, the row counts the old file's lines, read
  as a deletion from the same diff re-run with `--no-renames` for the old
  path, as a `git rm` of it would count. Both rename rules hold whether git
  reads the rename as text or as binary (a NUL byte early in the test-side file
  can make the whole row `-`): the recount reads the non-test side on its own, and a
  binary recount counts nothing and lands in `binaryPaths`. A rename with
  both paths on the same side of the test pattern counts as git's `-M` row.
- **`attributesTouched`** is true when any row read for the count, test and
  binary rows included, or a rename's old path, is a file named
  `.gitattributes`. U4 prints it as a warning line and U6's
  shadow log flags it. A base-branch merge that brings in base's own change
  to the file cleanly does not set it.
- **`binaryPaths` lists every path whose row was `-`**, in commit order.
  KTD5 skips binary rows, but a pull request's own `.gitattributes` (`-diff`)
  can make a text file read as binary, so the gate gets the paths to print.
- **The floor**: `git patch-id --verbatim` needs git 2.39 or newer. An older
  git answers it with exit 129 and a usage line, so that exit from the
  patch-id call throws a `TransportFailure` whose reason names the floor,
  `git 2.39 or newer is required (git patch-id --verbatim)`, whatever its
  stderr. So does any git call whose stderr says `unknown option` or
  `unrecognized argument`, as `--remerge-diff` gets before git 2.36. The
  README's requirements list gains git 2.39 or newer and an authenticated
  `gh` beside Node and jq.

## G4. The test pattern

Copy `TEST_PATTERN` from Compound Engineering 3.27.0,
`skills/ce-code-review/scripts/review-scope.py`, with a comment naming that
file and version so the gate and the reviewer agree on what a test is. Its
last alternative is case-sensitive inside a case-insensitive pattern
(`(?-i:…)`); in JavaScript write it as two patterns, one with the `i` flag
for the first three alternatives and one without for the
`Test|Tests|Spec` class-file suffix, rather than relying on regexp modifiers.

## G5. The tests the unit adds, beyond its scenarios

- An old git: a stub runner answers the patch-id call with exit 129 and
  `usage: git patch-id [--stable | --unstable]`; `patchId` throws a
  `TransportFailure` whose message names git 2.39. An `unknown option` stub
  on `patchId` and on `hasCommit`, and an `unrecognized argument` stub on
  `remergeNumstat`, do the same.
- A reviewed commit absent from the repo: `hasCommit` answers `false`, and
  does not throw. A checkout that is not a repository throws.
- A head with no check suites: `firstSuiteAt` answers `null`.
- `gh` returns a page of reviews whose entry lacks `state`: a
  `TransportFailure` naming `botReviews`. One with a null `commit_id`, no
  `submitted_at` and a null `user` reads as nulls.
- A repository whose own config and `.gitattributes` set every pinned
  option and a textconv driver gives the same answers as one without them.
- A file literally named `src => test/x.js` counts its lines; a clean merge
  of a branch that is not the base counts its lines and is listed; a
  `-diff` attribute's path appears in `binaryPaths`.

## G8. Residuals

- **A pull request can steer its own counts through `.gitattributes`.**
  The lead's clone reads attributes from its work tree (G1), so a pull
  request that adds `-diff` or a `merge=` driver changes how its own lines
  are read. That is forgery by the author on the lead's machine (KTD11), so
  it is made visible rather than engineered out: `binaryPaths` names every
  path read as binary, and `attributesTouched` flags any change to a
  `.gitattributes`.
- **A kept modify/delete conflict over-counts.** A base-branch merge whose
  modify/delete conflict was resolved by keeping the file leaves a notice
  with no row, so it counts its whole first-parent diff. That fails closed:
  more review, never a pass it should not get.
- **Found in the last review and left as residuals** (the stopping rule):
  a text file with a NUL byte in its first 8000 bytes reads as binary with no
  attribute, and shows only in `binaryPaths`; settings on the lead's side,
  not the pull request's, are not all pinned or cleared (`GIT_CONFIG_*`,
  `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY` and `GIT_NO_REPLACE_OBJECTS` in
  the environment, `core.bigFileThreshold`, `merge.renames` and
  `merge.directoryRenames`); some failure branches have no test of their own
  (an account's `type`, `firstSuiteAt`'s earliest-row choice and bad
  timestamp, a missing per-commit numstat, a signal-killed process).
- **The stopping rule.** After this unit's last review, a new finding in the
  class "configuration, attributes or environment a pull request controls
  steers git's output" is recorded here as a residual, not fixed in U3.
